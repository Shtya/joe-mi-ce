# Database Recovery & Reconstruction Strategy

**Status: PROPOSED — awaiting validation. No data will be inserted until this mapping is approved.**

Base state: April 2026 backup of the `gatemea` project database (PostgreSQL).
Evidence: 3 Excel exports generated by the application itself.
Goal: April backup + report evidence → reconstructed database, idempotently, with every row classified CONFIRMED / PROBABLE / UNRESOLVED.

---

## 1. Schema facts that drive the recovery

(Verified against `entities/`, `src/journey/`, `src/export/`, `src/reports/`)

- **All PKs are UUIDs** (`CoreEntity`: `id uuid`, `created_at`/`updated_at timestamptz`, `deleted_at` soft-delete). No sequences to resync. Recovered rows get fresh UUIDs; April-backup rows are never re-keyed.
- Schema is managed by `synchronize: true` (no migrations). The recovery DataSource must run with `synchronize: false` against the restored backup.
- Everything is scoped to `project` row named **`gatemea`** (hard-coded in `src/reports/reports.service.ts:1453`). `journeys.projectId` is a NOT NULL scalar uuid — the project id must be read from the restored backup, never assumed.

### Dependency map (child → parent)

```
countries → regions → cities → branches → chains(→project)
                                  branches → users (supervisor), project
users → roles, branches (home branch)
shifts → project
journey_plans → users, branches, shifts, users(createdBy)
journeys → users, branches, shifts, journey_plans(nullable), users(createdBy); projectId scalar NOT NULL
check_ins → journeys (O2O, journeyId, SET NULL), users
stocks → products(→project, brands, categories), branches   [UNIQUE (product, branch)]
audits → users(promoter), branches, products                [UNIQUE (branch, product, promoter, audit_date)]
sale → users, products, branches
```

### Insertion order

1. Reference data check/creation: chains → cities → branches → users (supervisors) → shifts
2. `journeys` (needs user, branch, shift, projectId)
3. `check_ins` (needs journeyId)
4. `stocks` upsert
5. Validation + reports

## 3. Column mapping — `Unplanned` sheet → `journeys` / `check_ins`

Verified against `Journey`/`CheckIn` entities and `src/export/export.service.ts:579-677`.

| Excel column | Target | Rule |
|---|---|---|
| `user username` | `users.username` → `journeys.userId`, `check_ins.userId` | Exact unique match in April backup. No match → UNRESOLVED (never auto-create promoters from attendance evidence without approval) |
| `user name` | `users.name` | Cross-check only; mismatch → flag for review, username still wins |
| `city name` | `cities.name` | Branch disambiguation |
| `Chain` | `chains.name` | Branch disambiguation |
| `branch name` | `branches.name` | Match on (branch name + chain name + city name), normalized (trim/case/whitespace); fuzzy matches flagged PROBABLE |
| `date` | `journeys.date` | Stored as-is (Saudi calendar date, `date` column — no TZ shift) |
| `status` | `journeys.status` | Values match the enum exactly: `absent` (257), `closed` (658), `vacation` (5), `unplanned_absent` (1) |
| `Check in time` + `date` | `check_ins.checkInTime` | Combine as **Asia/Riyadh wall clock → UTC `timestamptz`** (DB stores UTC; reports add +3h, `reports.service.ts:529`). `-` → no check-in |
| `Check out time` + `date` | `check_ins.checkOutTime` | Same; if time < check-in time, date+1 (midnight crossing) |
| `Check in image` | `check_ins.checkInDocument` | Strip host → `/tmp/checkins/<file>` path format used by `multer.config.ts`. Physical files live on the production server (`ce-api.joe-mi.com/tmp/...`) — recovery can optionally download them into `./tmp/checkins/` |
| `Check out image` | `check_ins.checkOutDocument` | Same |
| `shift startTime` / `shift endTime` | `shifts` → `journeys.shiftId` | Lookup shift by (startTime, endTime, project). Observed: `09:00–18:00`, `15:30–23:30`, `15:00–?`. Missing shift → UNRESOLVED or create flagged minimal shift (decision needed) |
| `Duration`, `Late Time`, `Total Late Time`, `Status Code` | — | **Computed fields, not stored.** Recomputed during validation and compared against the report to prove correctness |
| — | `journeys.type` | Inferred from status prefix: `unplanned_*` → `unplanned`, else `planned`. To be confirmed against `export.service.ts` filter for this export |
| — | `journeys.journeyPlanId` | **Not recoverable from the report.** Proposal: NULL (journey exists without plan) — plan reconstruction would require inventing `days[]`, `createdBy`, visit order |
| — | `journeys.createdBy` / `check_ins.geo` / `noteIn/out` | Not in report → NULL, never invented |
| — | `isAutoClosed` | `closed` rows with check-out image → false; `closed` with no check-out time → likely auto-closed (PROBABLE) |

**Natural key (idempotency):** `(userId, branchId, shiftId, type, date)` — matches the app's own dedupe rule in `createUnplannedJourney` (`journey.service.ts:967`). Re-running the recovery finds the existing row and skips.

**Check-in ↔ journey consistency** (mirrors `recoverCheckInTimes`, `journey.service.ts:2265`): status `closed`/`present` requires a `check_ins` row with `checkInTime`; `absent` rows get no `check_ins` row.

## 5. Column mapping — `Stock` sheet → `stocks`

- Row header = `products.name`, column header = `branches.name`, value = `stocks.quantity`.
- Upsert on the real UNIQUE key `(product_id, branch_id)`.
- Product or branch not found in backup → UNRESOLVED row, no insert.
- This restores a **current-state snapshot**, not history — acceptable because `stocks` is a current-state table by design.
- `Out of Stock` sheet used only to cross-validate (`qty ≤ 0` ↔ OOS marker).

## 7. Implementation — recovery endpoint (approved design)

**Decisions confirmed with the project owner (2026-08-13):**
- The April backup is already restored on the server DB the app connects to — recovery runs **through the application itself**, as an API endpoint, with **upsert (create + update)** semantics.
- SixSeven sales pivot → **synthetic aggregate sale rows**, clearly flagged (`userId = recovery.system`, `branchId = NULL`, confidence PROBABLE).
- Journey plans → **reconstruct minimal plans** per (user, branch, shift) with observed weekdays in `days[]`, `is_active = false` so the cron never generates journeys from them.
- The 3 provided Excel files are the complete evidence; May–June attendance is a documented unrecoverable gap.

### Endpoint (async)

Imports run in the background to avoid gateway timeouts on large reports.

**Start a job:**
```
POST /api/v1/recovery/import?type=attendance|branches|stock|sales|monthly&project=gatemea&dryRun=true&saleDate=2026-08-12
```

- Multipart field `file`: the Excel report.
- Response: `{ "jobId": "...", "status": "pending", "message": "..." }`.
- **`dryRun` defaults to `true`**: all work runs in one transaction that is rolled back — the result shows exactly what *would* be created/updated without writing anything.
- `dryRun=false` applies the upserts and commits. On any error the transaction rolls back.
- Optional protection: if `RECOVERY_TOKEN` is set in the environment, calls must send it as `x-recovery-token`.
- `project` selects the target project (`gatemea` for the three original reports, `taqnia` for the monthly report) — data is always assigned to that project.

**Poll for results:**
```
GET /api/v1/recovery/jobs/:jobId
```

Job status is one of `pending | running | completed | failed`. When `completed`, the response contains `summary` and `rows`. When `failed`, `errorMessage` is set.

| `Sales by Model` | 342 | Product enrichment: brand/category/SKU/model find-or-created and attached (products matched by model, then name) |

### Code

- `src/recovery/recovery.controller.ts` — `POST /recovery/import` and `GET /recovery/jobs/:id`, validation, token check.
- `src/recovery/recovery.service.ts` — parsing + transactional upsert logic, reusing the project's actual TypeORM entities (`User`, `Branch`, `Chain`, `City`, `Shift`, `JourneyPlan`, `Journey`, `CheckIn`, `Product`, `Stock`, `Sale`).
- `src/recovery/recovery-job.entity.ts` — `recovery_jobs` table that stores job status, summary, and row-level results.
- `src/recovery/recovery.types.ts` — per-row result model: action ∈ EXISTING/CREATED/UPDATED/SKIPPED/DUPLICATE/UNRESOLVED, confidence ∈ CONFIRMED/PROBABLE/UNRESOLVED, natural key, resolved DB ids.

### Upsert / idempotency rules

| Entity | Natural key | Existing row | Missing row |
|---|---|---|---|
| users | `username` (case-insensitive, incl. soft-deleted) | restore/backfill name, project, role, mobile, is_active | create with role (`promoter` for attendance users, `supervisor` for branch supervisors), `project_id`, **initial password = username** (argon2-hashed, so they can log in immediately and change it later) |
| chains | name + project | reuse | create (PROBABLE) |
| cities | name | reuse | create attached to first region (PROBABLE) |
| branches | name + chain + city in effective project (fallbacks: name+chain → unambiguous name-only → punctuation-insensitive → cross-project, PROBABLE) | restore if soft-deleted | create (PROBABLE) |
| shifts | startTime + endTime + project | reuse | create (PROBABLE) |
| journey_plans | user + branch + shift + project | reuse, merge weekday into days[], force is_active=false | create minimal, is_active=false, createdBy=recovery.system |
| journeys | user + branch + shift + type + date (incl. soft-deleted) | restore / update status / link plan | create |
| check_ins | journeyId (O2O) | restore / update times+documents | create; closed-without-checkout → isAutoClosed (PROBABLE) |
| stocks | (product_id, branch_id) UNIQUE | update quantity | create |
| sale (synthetic) | productId + recovery.system + qty + sale_date + branchId NULL | DUPLICATE, skip | create aggregate row (PROBABLE) |

All recovered rows are attributable: `journeys.createdBy` / `journey_plans.createdBy` / synthetic `sale.userId` point to the dedicated inactive user **`recovery.system`**, so everything the recovery touched can be found (and, if validation fails, removed) with simple audited DELETEs — that is the rollback strategy.

### Cross-project row routing (unplanned export)

The `unplanned_export_1785146807680.xlsx` file is **not single-project**: it contains ~130 Xcite/Kuwait rows and ~26 `Saco Thakasussi 1103` rows whose branches exist only under **Bissell Saudi**, plus near-miss names (`Saco World KA` vs gatemea's `Saco World K. A.`, `Extra Ghadeer R20` vs `Extra Ghadir R20`). The attendance pipeline therefore resolves the project **per row**:

1. Effective project = the row user's `project_id` (fallback: the `project=` query param — use `project=Bissell%20Saudi` since this export is Bissell Saudi's; users without a project get routed by their branch match anyway).
2. Branch resolution inside that effective project: name+chain+city → name+chain → unambiguous name-only → punctuation-insensitive (`regexp_replace(name, '[^a-zA-Z0-9]', '', 'g')`, PROBABLE).
3. If still unmatched: cross-project search (exact then punctuation-insensitive, disambiguated by chain name). On a unique hit the row is **reassigned to that branch's project** and flagged PROBABLE ("cross-project branch match — verify").
4. Chain, shift, journey_plan and journey are then resolved/created in the winning project, so a single run distributes the 921 rows across Bissell Saudi / gatemea / taqnia correctly. Chains/cities are only *created* when a branch is created — never as a side effect of a failed lookup, so a gatemea-only chain is never created under Bissell Saudi.
5. Ambiguous cross-project hits (same branch name in several projects, chain doesn't disambiguate) → UNRESOLVED, nothing inserted.

### Response = recovery mapping report

When a job is `completed`, `GET /recovery/jobs/:id` returns the full report. Every report row produces a JSON entry: source sheet + row, entity, action, confidence, reason, human-readable natural key, and the resolved database ids (userId → branchId → shiftId → journeyPlanId → journeyId → checkInId). The `summary` block gives the counts required by the spec (existing/created/updated/skipped/duplicates/unresolved).

## 8. Runbook

1. Deploy/restart the app on the server (the DB there already holds the restored April backup). The `recovery_jobs` table will be created automatically on startup (TypeORM `autoLoadEntities`).
2. Start a dry-run job for each report. The response contains a `jobId`; poll `GET /recovery/jobs/:jobId` until `status` is `completed` or `failed`.
   **The unplanned export is Bissell Saudi's report** — run it with `project=Bissell%20Saudi` as the default; rows whose user/branch belong to gatemea or taqnia are auto-routed to those projects by the cross-project resolution:
   ```bash
   # Attendance
   JOB=$(curl -s -F "file=@unplanned_export_1785146807680.xlsx" \
     "https://ce-api.joe-mi.com/api/v1/recovery/import?type=attendance&project=Bissell%20Saudi&dryRun=true" | jq -r '.jobId')
   curl -s "https://ce-api.joe-mi.com/api/v1/recovery/jobs/$JOB" | jq

   # Branches
   JOB=$(curl -s -F "file=@branches_export_1786520160222.xlsx" \
     "https://ce-api.joe-mi.com/api/v1/recovery/import?type=branches&project=gatemea&dryRun=true" | jq -r '.jobId')
   curl -s "https://ce-api.joe-mi.com/api/v1/recovery/jobs/$JOB" | jq

   # Stock
   JOB=$(curl -s -F "file=@gatemea_report_6_7_2026_08_13_081000_036.xlsx" \
     "https://ce-api.joe-mi.com/api/v1/recovery/import?type=stock&project=gatemea&dryRun=true&saleDate=2026-08-12" | jq -r '.jobId')
   curl -s "https://ce-api.joe-mi.com/api/v1/recovery/jobs/$JOB" | jq

   # Sales (gatemea standalone sales export)
   JOB=$(curl -s -F "file=@sales_export_1785656048354.xlsx" \
     "https://ce-api.joe-mi.com/api/v1/recovery/import?type=sales&project=gatemea&dryRun=true" | jq -r '.jobId')
   curl -s "https://ce-api.joe-mi.com/api/v1/recovery/jobs/$JOB" | jq
   ```

3. Review UNRESOLVED / PROBABLE rows; fix mapping issues if any; re-run (safe — idempotent).
4. Re-run the same three calls with `dryRun=false`, polling each job until completion.
5. Validate in the DB: row counts vs. reports (921 attendance rows), no duplicate journeys per natural key, spot-check Duration/Late Time recomputation, verify timezone boundaries (checkInTime stored UTC, +3h = report time).
6. Take a fresh backup after validation.

## 9. Open items / known limitations

- Check-in image **binaries** live on the server's `/tmp/checkins/` filesystem; the recovery restores the DB path columns only. If files were also lost, they cannot be recovered from the Excel (URLs only).
- Synthetic sales lose chain attribution (no chain column on `sale`); chain is recorded in the recovery report output only.
- `Branches Is Active` has no target column on `branches` (lifecycle = `deleted_at`); intentionally not mapped.
- May–June attendance: no evidence exists; not reconstructed.
- **Login-readiness**: every recovered user gets `project_id` and a role (`login()` dereferences `user.role.name` — a NULL role would crash it), and `users.branchId` is synced to the branch of the user's latest journey, mirroring the app's check-in behavior. All user fields present in the reports are applied: name, mobile (with unique-index conflict guard — a mobile already held by another account is skipped and flagged), avatar URL, brand-assignment mode, is_active. Users who already exist in the April backup keep their original passwords; newly created users get **password = username** (argon2) so they can log in right away — they should change it on first use.
